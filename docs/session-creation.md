# New Session: project and starting branch

Run `npm run tui`, then press **n**. A small form opens inside the existing workspace. Opening the form or reading branches does not start a model or create a worktree.

1. **Agent** defaults to **Codex · local** on a new standard server. Shift+Tab focuses Agent; arrows choose a preset, then Tab returns to the project/branch field; **Fixture · no model** uses the built-in sample. Local mode shares OS permissions and is not a security sandbox.
2. **Project** starts at the TUI process's launch directory, even when attaching to a daemon launched elsewhere. Type/paste a project folder; relative paths and `~/` are resolved by the TUI. Ctrl+A / Ctrl+E / Ctrl+U and ordinary text editing work here. Tab lists folders under the current path or matches a partial folder name. A unique match completes the path with `/`; otherwise use arrows/Tab and Enter to fill a candidate. The first Esc dismisses the folder list, the next closes New Session. Enter without an open list reads local branches. A folder without Git offers explicit initialization and a first commit; an empty Git repository offers the first commit. Subfolders of an existing repository still require its root.
3. **Branch** initially selects the source's current local branch, or its current commit when detached. Type to filter, use ↑/↓ to choose `main` or a saved `workbench/run-…` branch, then Enter to create. Ctrl+B returns to the folder field. Esc closes the form, including an unfinished read-only lookup. A late lookup cannot reopen it.

Creation makes a **new** `workbench/run-…` branch and worktree at the selected commit. It does not switch the source checkout, include its pending edits, reuse another Run's worktree, or restore an old agent conversation. A branch that changed since inspection must be reloaded. The form shows up to 256 local branches, including the current branch; it does not fetch remote branches.

The browser's **New** action provides the same agent/folder/branch choices. Use an absolute path there, **Load branches**, then **Create Session**. Fixture and fixed configured presets hide the project fields. Both clients leave the form available after an error and require an explicit retry.

Folder candidates use an `ls`-style grid, sorted down each column, with at most three visible rows. The column count follows the available terminal width; a range shows which candidates are visible. Arrows move between cells, including across pages, and Tab advances to the next candidate, wrapping at the end. Blue names are folders (`/`), magenta names are directory links (`@/`), and cyan inverse video with `>` marks the current choice. Long names shorten with `…` while preserving the type suffix; Enter always fills the full path. Names and markers remain readable without color. Left/right edit the path again after the list closes. Editing a path closes old suggestions; late reads cannot overwrite the new input or an Agent selection. Parent folders do not need Git; only the final project inspection does. `../` browses upward, and a dot prefix such as `~/Developer/.` includes hidden folders. This is TUI completion; browser forms keep ordinary Tab focus navigation.

## Initialize a project

When the selected folder has no Git repository, the form asks **Initialize Git and commit current files?** It defaults to **No**. Select Yes with the arrows/Tab and Enter, or type `y`; `n`, No or Esc returns to the folder without writing files. Paste and key-repeat do not confirm. The browser shows the same explicit **No, choose folder** / **Yes, initialize** actions. Opening or inspecting remains read-only.

Yes runs `git init` with a `main` branch and creates **Initial project snapshot** from current non-ignored files. An already initialized empty repository keeps its branch and creates only the first commit. Empty folders use an empty initial commit, since worktrees need a commit. Existing `.gitignore` rules apply. The configured Git identity/signing policy applies; missing identity fields use `Agent Workbench <workbench@localhost>` for this initial commit only, without changing Git settings. Successful initialization returns to the normal branch chooser; creating a Run remains a separate explicit action.

Execution rechecks the canonical folder's filesystem identity and Git state before mutation, and a temporary `.workbench-init.lock` serializes initialization across clients/daemons. A duplicate request after success returns the existing project without committing later edits. Changed paths, existing repository subfolders and invalid Git metadata require a fresh inspection. Commit/signing failures preserve current files and any initialized/staged Git state; reload the folder to confirm again. A lost reply is never automatically replayed: inspect again to determine whether the initial commit exists. After a crash, an operator may remove a leftover lock only after confirming initialization is no longer running.

## Continue saved work

Close a Run with `x`. A clean worktree is collected; changed files require the explicit `c` / `:commit <message>` save. Keep the branch name shown in the receipt. Next time, choose the same project and that branch in New Session. Its committed code appears in a fresh worktree. No remote push, merge or branch deletion occurs. See [worktree operation](worktrees.md).

## Multiple projects and Roadmaps

One daemon can host Runs from different Git projects. Run labels identify their project until a Task supplies the label. Selecting a Run selects its actual Project tree, working path, branch and project Roadmap. Linked worktrees of the same repository share the main checkout's planning identity; different projects keep separate plan files and Task context.

New Runs stay **Direct** until explicitly attached. Use `:roadmap <title>` for the selected project, or `:track P.T` to attach an existing Task. A saved code branch and a saved Roadmap are separate: selecting a branch does not automatically choose a Task or pass a stage. Plan files survive restart; Run associations, conversations and approvals do not. See [Roadmap operation](roadmap-operation.md).

## Trusted settings and compatibility

Normal project selection needs no environment variable or launch JSON. The standard server supplies a trusted local Codex preset using `.workbench/local-runs` under its startup directory and, when present at startup, the existing `~/.codex/auth.json` as the private-copy login source. It does not copy global Codex settings or write refreshed credentials back. Provider connectivity and an accepted login are still required. Other sign-in flows and parallel refresh behavior remain unverified; see [local execution](local-execution.md).

`WORKBENCH_LAUNCH` remains optional operator configuration for adapter/login/storage/managed-worker settings. A configured local Codex worker can create Sessions in different chosen projects; a fixed managed/HTTPS/sample preset uses its configured source. Ordinary commands accept a preset ID, project path and displayed base revision, never executable, credential or storage settings.

An older daemon keeps its original `n` behavior and does not gain these endpoints merely by reopening the TUI. Start a new server on an unused port to test this slice while preserving its Runs, for example `WORKBENCH_PORT=4218 npm run tui`. Existing servers are never replaced automatically. `q` detaches; stopping a server affects its managed Runs.

## Module map and public Interface

- `execution.inspectLocalProject(path)` validates a Git root and returns canonical project identity, HEAD/current branch and bounded local branch metadata. A `ProjectInitializationRequired` error carries validated `ProjectInitialization` details for a non-Git or empty Git folder. `initializeLocalProject(details)` owns explicit init/initial snapshot, state/identity checks and locking. `Source.directory.base` pins a displayed branch/HEAD revision. Execution validates it again when creating the worktree; all Git operations remain inside execution.
- `work.createProjectWorkspaces` owns project registration, process-local Run ownership, per-project `Work` instances and prompt routing. It rejects cross-project Run/Task attachment. Since 2026-10-23 its `startSession` performs the inspect → register → launch → associate sequence for New Session, and `overview()` ranks next actions ([Project overview](project-overview.md)). Existing single-project `createWork` remains available.
- App composition supplies trusted presets and exposes authenticated `POST /api/project`, `POST /api/project/folders`, `POST /api/project/initialize`, `new-session` and `project-work` commands. Initialization requires inspected details and `confirm: true`; its bounded request allows up to two minutes for hashing/signing. State advertises `features.newSession` / `features.folderCompletion` / `features.projectInitialization`, session options and project/work snapshots. Older daemons retain manual Git setup. Legacy `start` and unscoped work commands keep their configured-project behavior.
- `execution.listProjectFolders(path)` reads one directory level before a Run exists, scans at most 4,096 entries and returns at most 200 matching folder names/paths/types. No file contents or recursive Git scans. Directory links are identified and traversed only after explicit choice; hidden names need a dot prefix. A truncated result asks for a narrower prefix, never auto-completes a possibly non-unique match. This source chooser is separate from Run-scoped `listDirectory`.
- TUI/browser render the form and selected-project projection. They cannot override executable/auth/storage settings. Lookup generations and server-instance changes invalidate old UI state; mutations are never automatically replayed after a lost reply.

Existing bounds remain: four active Runs, 64 created Runs per daemon and bounded live events. No new worktree-count setting or Run history was added. Crash reconciliation, remote branch selection, worktree reuse, independent Review/check evidence and Human Review acceptance remain later work.

Validation: public execution/workbench tests cover saved-branch continuation, source preservation, canonical linked-worktree identity, stale/invalid refs, cross-project plans/prompts/files, restart without old Runs, actual Ink input and cancelled lookups. Layout captures cover 120×36, 80×24 and 60×20; browser acceptance covers desktop dark and mobile light. These are rendered Ink frames, not physical-terminal acceptance. The real Codex harness also exercises the form on disposable Git source before its edit/approval/cancel/commit workflow.
