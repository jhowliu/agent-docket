# M0 browser test workbench

Mode: Operate. The user asked to prioritize an interface so the current implementation is easier to test, then confirmed this surface remains a browser demo. The separate Ink TUI has since been implemented; see tui-surface-brief.md. Inherit DESIGN.md's native mono, paired colors, fine rules, roster, inline decisions and detail tabs.

- **Job:** start two trusted fixture Runs, trigger independent permission requests, allow one/reject the other, inspect each Run's messages/diff/timeline, ask and answer a text question, and cancel a waiting Run without entering a provider CLI.
- **Composition:** follow the user's newer oat-agents screenshot and request for maximum simplicity: one quiet header, one agent roster, one timeline. No persistent sidebar, duplicate agent navigation, guide prose, event-count column, receipt panel or always-open composer. Name the source “Built-in fixture project” and each Run “Run N”. Default to active work and Timeline; history remains a filter. Keep Live/Diff as small tabs. Project/source details open with p, Run metadata/scenario controls with s, composer with i; Esc or a successful unchanged-draft send closes the composer. Actual pending decisions appear as one compact row with optional details. Acceptance/delivery status goes to the existing footer once per change. Services stays in the separate prototype.
- **Behavior:** poll authoritative snapshots and bounded event cursors; preserve selection/drafts/disclosures across updates; disable mutations while disconnected or in flight; permission actions use opaque domain IDs and provider-supplied choices. Cancellation invalidates pending decisions. Idle means a prompt ended, not verification passed. Keyboard: j/k selection, h/l or1–3 tabs, n start, i compose, Esc navigation, a/r once-only answer of the focused/first pending item, w next waiting Run, p project, s Run options, : command mode, ? help. Typing/IME/modifier keys never trigger navigation or approvals. Held action keys do not repeat operations. Commands are allowlisted UI actions, not a shell.
- **States:** connecting, no Runs, starting, idle, running, awaiting permission, accepted, transport-delivered, stale, cancelling, cancelled, abnormal exit, disconnected/retry. Empty states explain the next action. Repeated decisions never replay work. Responsive desktop/mobile use the incumbent system and keyboard-operable tabs.
- **Scope:** a Node loopback server adapts the public execution/attention Interfaces; fixture processes work in temporary copies. No model, credentials, shell command execution from browser input, real service launch, task pipeline, recovery claim, or GitHub publication. Closing a browser tab does not stop the server; stopping the server cleans its Runs. The separate Ink entry now shares this transport; this brief still describes only the browser renderer. Keymap details are in `docs/tui-keyboard.md`.

THESIS: Make the real M0 control loop observable and operable from one screen.

FINISH: inspect desktop/mobile screenshots in bounded passes, run the mechanical detector once, obtain a fresh finish review, and compare against the incumbent DESIGN.md without changing its tokens.
